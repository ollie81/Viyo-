========================================================================
1. WHAT IS ALREADY IMPLEMENTED AND TESTED
========================================================================
Backend: FastAPI on Railway. App: Flutter, web and Android. Database: Supabase. Video storage: Bunny Stream.

Credits and money
- Studio credits are separate from Viyo Watch coins.
- 1 credit = $0.01 of net revenue.
- Price of any job: credits = cost / (1 - 0.25 margin) / $0.01, rounded up, minimum 1.
- Bought and promotional credits are kept as separate lots. Promotional credits are spent first and can expire.
- Every job: hold the estimated credits, then capture the real cost (never more than the hold), then return the rest.
- On failure: release everything. The creator pays nothing. Viyo absorbs any provider cost already spent.
- Text jobs hold 1.6x the estimate, because output length varies; the unused part comes back.
- A double tap uses the same idempotency key, so one job and one charge.
- Admin can grant credits (with a reference) by user id or @username.
- Credit packs are defined, but there is NO checkout yet.

Job system
- Jobs live in Postgres. Workers claim jobs, send heartbeats, and complete or fail them.
- A job from a crashed worker is picked up again after 180 s.
- "Provider busy" errors (429/503) are retried. Other failures refund.
- Cancel before a job starts gives a full refund.
- Two lanes: generation and render.
- Each user can have at most 30 open jobs, and there is a rate limit per user.

Production pipeline (one job type per step; each shows its price first)
- Script: a screenplay from title, idea, genre, format, length, language and 9:16 or 16:9. The creator can edit it.
- Breakdown: splits the script into a cast (visual descriptions) and scenes (heading, one visual prompt, dialogue, duration, emotion per line).
- Portrait: a reference image per character (gemini-3.1-flash-image).
- Scene image: up to 4 cast portraits are sent as references. 1K, or 2K on "High quality".
- Scene video: one Omni 1.2 Flash clip starting from the scene image, with its length matching the scene.
- Voice: one TTS call per line in the character's saved voice, then the lines are joined.
- Render (FFmpeg):
  - slow push-in on stills, burned-in captions;
  - voice levelled to -16 LUFS; the clip's own sound kept, lower under voices;
  - up to 4 synthesised sound effects per scene;
  - optional creator music, quieter under speech (tested at about 8 dB);
  - H.264 at CRF 19, AAC 192k;
  - the result goes to Bunny Stream.
- Download: Bunny MP4 or a signed link. "My Productions" downloads were tested live: owner only, link valid for 1 hour.

Stage 0 (critical fixes): done
- Video moved to gemini-omni-1.2-flash ($12 per million output tokens = about $0.07/s at 720p). Each request asks for the clip length explicitly.
- Re-running the breakdown never deletes paid work:
  - Same place and same lines: the scene is kept as it is.
  - Same place, new lines: the picture is reused, but there is a new voice recording.
  - Any scene that is replaced is first copied to an archive table.
  - All of this happens in one SQL transaction. A test proves that nothing changes if any part fails.
  - The creator must confirm first, and no credits are held before that.
- An invalid voice, or a speaker not in the cast, stops the job and refunds it. This is checked before credits are held and again in the worker. It is never quietly read by the narrator.
- The project language reaches the breakdown. Dialogue is copied word for word; picture prompts are written in English.

Stage 1 (permanent character voices): done
- Character record: voice_provider, voice (the provider's voice id), voice_style (an 80-character delivery note), voice_language, voice_locked_at, voice_changed_at, identity_id.
- The voice is assigned once, at creation, and is never picked again on breakdown, regeneration or a new episode.
- Each scene records which voice each character used (audio_voices).
- Changing a recorded voice needs confirmation:
  - the old audio is kept and flagged;
  - the change is logged in studio_voice_changes;
  - the affected scenes are offered for re-recording, with the price shown.
- "Next episode" copies the cast with voice, note, portrait and identity.
- At breakdown, a character returning later in the series gets their old voice and look back.
- A voice list with samples. The admin tool makes samples only with an explicit "spend" flag; it hasn't been run.
- TTS now uses Google's documented Interactions API for 3.8. The old code added a second WAV header; that bug is fixed.
- The app now keeps per-line emotions when a scene is saved; this was another fixed bug.

Test results (latest runs)
- Backend: 350 passed, 0 failed (full suite). Includes 21 Stage 0 tests and 16 Stage 1 voice tests.
- App: no analyzer errors, 9/9 tests passed, the web release build works.
- Not tested: real provider calls, and a manual click-through of the new screens.

4. CHARACTER AND VOICE CONSISTENCY
========================================================================
Voices: strong
- The same prebuilt voice id gives the same sound for that character in every scene, regeneration and episode. This is enforced in code and tested.
- Delivery (emotion, pacing) still varies a little per recording. Google offers no seed or exact-repeat setting.
- Google advises a short, unchanging style note to reduce drift; we follow that.
- Wording to use: "same voice", NOT "identical performance".

Faces and look: medium
- Each character has one portrait, sent as a reference to every image with them in it.
- Faces stay recognisable most of the time. Hair, clothing, hands and backgrounds can drift between images. No current model guarantees identical faces.
- Stage 2 (outfits, 3-angle sheets, location references, locked style) and Stage 3 (single-shot regeneration) are the practical fix.

Across episodes
- Characters are copied with an identity link.
- A returning character gets the same voice, note, description and portrait.
- The portrait file is shared, not duplicated.

Lip sync: unproven
- TTS voices and Omni's built-in speech are different voices.
- Default approach: dialogue over stills, reaction shots, over-the-shoulder or wide shots.
- Premium talking shots need a live test, giving the TTS line to Omni as an audio reference.

- Suggested margins:
  - 25% on images, music and render;

  - a small minimum per episode, so cheap steps aren't run at a loss on retries.

  - failure gives a full refund;

  - cancel before start gives a full refund;
  - content blocked by the AI is not charged;
  - the charge is never more than the hold.
- Missing: a per-episode approved budget with a pause on overspend (Stage 4), and chargeback handling (not built yet).

7. WHAT CAN REALISTICALLY BE PROMISED TO PAYING CREATORS
========================================================================
Safe to promise (once the live test passes)
- Bring an idea: Viyo writes the script, creates the cast, voices every line, makes the pictures, adds music and sound, and delivers a finished, downloadable video.
- No need to upload voices, music, pictures or sound effects.
- Each character keeps the same voice across scenes and episodes.
- You see the price before anything is made, and you never pay for anything that fails.
- Redo a single scene without redoing the episode.
- Your film is yours to download and share outside Viyo; publishing on Viyo is optional.

Do NOT promise
- Identical faces in every shot ("consistent characters" is fine; "identical" is not).
- Identical voice performance every time.
- Lip-synced talking characters (until tested).
- Full copyright ownership of AI-generated material.
- Any fixed video quality level before the live test.
- Unlimited generation.
